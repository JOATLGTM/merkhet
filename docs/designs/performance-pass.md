# Design: Performance pass for the Merkhet board

Generated by /office-hours on 2026-09-27
Branch: main
Repo: JOATLGTM/merkhet
Status: APPROVED
Mode: Startup (intrapreneurship: internal tool for firm staff)

## Problem Statement

Staff wait after everyday actions. Dragging a card to a new column, saving a
project, saving delegation and rejecting a gate all block on work the user does
not need to wait for: repeated full project loads, a second full page render,
and outbound email delivery. The board also ships every project ever created,
with its full activity history, to the browser on every view, so it gets slower
as the firm completes work.

## Status Quo

From reading the code (not yet measured): one drag-to-move runs about 9
sequential Supabase round trips across three full `getProject` loads, then
notification work (about 3 more), then 2-3 sequential Resend calls, all before
the action returns. The client then calls `router.refresh()`, which renders the
page a second time although the action already called `revalidatePath`.

## Constraints

- Next.js 16.3 with Cache Components enabled. Check `node_modules/next/dist/docs/`
  before using any Next API (per AGENTS.md).
- Supabase with RLS policies that are all `using (true)`.
- Client email went live on 2026-09-27 (`EMAIL_CUSTOMER_ENABLED=true`).
- The outbox row stays the durable record of every email.

## Premises (confirmed)

1. This is an internal staff tool. The goal is faster daily use, not growth.
2. The biggest pain is waiting after an action, more than first page load.
3. Fixes must not change behavior: same triggers, same recipients, same email
   content. **Clarified:** delivering an email a few seconds after the response
   instead of before it counts as the same timing. The trigger, recipients and
   content are what premise 3 protects.
4. Shared cross-user caching (`'use cache'` via a service client, bypassing RLS)
   is a separate decision and out of scope.

## Approaches Considered

- **A: Quick wins only.** Rejected: leaves unbounded payload growth and the slow
  delegation save in place.
- **B: Full list, phased (chosen).** Covers every finding except caching. Costs:
  the largest change surface of the three, two to three migrations, and changes
  to the email path days after client email went live. Those risks are handled
  by shipping the email-path change as its own deploy (see Rollout).
- **C: Measure first.** Rejected as a separate phase: the top problems are
  visible in code. Its useful part, a timing baseline, is kept as the Assignment.

## Recommended Approach: B, in three deploys

Ordering rule: post-action wait first (premise 2), then payload, then first-load
polish. Low-risk, low-effort first-load items ride along only where they touch
no data or email path.

## Rollout and Rollback

- Each deploy ships separately, email path (Deploy 2) on its own.
- After Deploy 2, watch `email_outbox` for a day. **Revert Deploy 2** if any row
  sits `pending` for more than 10 minutes without being swept, if any row reaches
  `sending` and stays, or if any trigger produces a different number of rows per
  event than before.
- A plain revert is enough for every item; the migrations only add things.

## Success Criteria

- **Measurement:** server duration of the Server Action request for a drag-to-move,
  read from the browser network tab (Timing, "Waiting for server response") on the
  deployed app, median of 5 moves. The same method is used for baseline and after.
- **Target:** at least 60% lower than the baseline recorded by the Assignment.
  Confirm or tighten the number once the baseline exists.
- One server render per mutation, not two.
- The board payload no longer contains completed projects or activity.
- Email parity: `npm run check:email`, `check:recipients`, `check:gates` and
  `check:creator` give the same results before and after. One manual drag on each
  of a customer-visible phase, a review gate and Permitting writes the same outbox
  rows (template, audience, recipients) as before.
- Lint, typecheck and a production build pass.

## Open Questions

- Does the Supabase project use asymmetric JWT signing keys? If not, item 5 keeps
  `getUser()` in the proxy and only the layout change ships.
- What is the account's Resend rate limit? The cap in item 12b assumes the default.

## Dependencies

- Next 16.3 docs for `after`, `revalidatePath` and `next/dynamic`.
- Migrations: the customer_id index (Deploy 1), `reject_gate` reflow (Deploy 1),
  the `sending` outbox status (Deploy 2), and `save_delegation` (Deploy 3).

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — consistency

**Problem**

> Deploy 1 is titled 'no email-path change', yet it changes the email path in three places. Item 3 changes the project object handed to the notifier in five mutations, rejectGate included. Item 9 changes rejectGate, which triggers gate email. Item 12a changes resolveAudiences, which resolves recipients. This contradicts the Rollout rule that the email path ships on its own in Deploy 2, and the coaching takeaway that anything reaching clients gets its own deploy.

**Remedy**

> Either move items 3, 9 and 12a (or their notifier and audience parts) into Deploy 2, or drop the 'no email-path change' label and apply the email parity checks and revert criteria to Deploy 1 as well.

### R2-2 — feasibility

**Problem**

> Item 1 has `enqueue` run inside the repo mutation and `deliver` run in `after()` in the Server Action, but it never says how the action learns which outbox rows to deliver. Item 2b shrinks action return values at the same time, and the repo functions would need to return the new row ids (or the action would need another way to find them), which widens their return types.

**Remedy**

> Define the handoff. For example, the repo functions return the enqueued outbox ids and the action passes them to `deliver`, or `deliver` picks up this event's `pending` rows by a correlation key. Exclude those ids from the 2b shrinking rule.

### R2-3 — completeness

**Problem**

> Item 1 splits `enqueueAndSend` and names only moveProject, markProjectComplete, uploadContractAndActivate and rejectGate. Item 3 says updateProject and changeProjectCustomer also run the notifier, and other callers of `enqueueAndSend` (other actions, route handlers, scripts such as email:send) are never listed. Any caller that is not updated after the split would enqueue rows but never deliver them until the sweep runs.

**Remedy**

> List every caller of `enqueueAndSend` and state, for each one, whether it gets `deliver` in `after()` or delivers inline (for scripts and non-request code).

### R2-4 — completeness

**Problem**

> Rows can get stuck in `sending` with no recovery path. This happens if `after()` is cut short after the claim, or if Resend accepts the email but the status update fails. Item 1b sweeps only `pending` and `failed`, so such an email is either lost or its state is unknown. The Rollout treats a stuck `sending` row only as a revert trigger, not as something to recover.

**Remedy**

> Define how stale `sending` rows are handled. For example, sweep `sending` rows older than N minutes and resend them with a Resend idempotency key tied to the outbox id, so a resend after an accepted-but-unrecorded send cannot duplicate the email.

### R2-5 — clarity

**Problem**

> Item 1b relies on `email:retry` to recover interrupted sends, and the Rollout says 'pending for more than 10 minutes without being swept'. The document never says whether `email:retry` runs on a schedule (cron, and how often) or only when someone runs it by hand. If it is manual, interrupted emails wait indefinitely.

**Remedy**

> State how and how often `email:retry` runs in production after Deploy 2, and add the scheduler to the Deploy 2 scope if one does not exist.

### R2-6 — completeness

**Problem**

> Item 12b claims that 'a retry running at the same time cannot send it twice', but the claim step is only described for the `deliver` path, from `pending` to `sending`. The document does not say that `email:retry` uses the same conditional claim for the `pending` and `failed` rows it sweeps.

**Remedy**

> Specify that `email:retry` claims every row with the same conditional update (from `pending` or `failed` to `sending`) before sending, and skips any row it does not claim.

### R2-7 — feasibility

**Problem**

> Item 12b caps concurrency at 2 calls and says this keeps it 'under Resend's default limit of 2 requests per second'. A concurrency cap is not a rate limit: two parallel calls that each take 200 ms send about 10 requests per second. The cap is also per `deliver` call, so concurrent requests' `after()` callbacks plus `email:retry` together can exceed any account limit. The original obligation, keeping delivery within Resend's rate limit, is still not met.

**Remedy**

> Use a real rate limit (spacing or a token bucket) or send sequentially, and define the handling of a 429 response (back off, and leave the row as `pending` or `failed` so it can be retried).

### R2-8 — scope

**Problem**

> Once item 1 moves delivery into `after()`, sending emails concurrently (item 12b) no longer shortens any user-visible wait. Premise 2 is about post-action waiting, and each event produces only 2-3 emails. The concurrency part adds rate-limit risk to the newly live client email path with no benefit the user can see. (The claim step still has value on its own for retry safety.)

**Remedy**

> Either drop the concurrency part of 12b and keep the claim step, or state the concrete benefit that justifies sending concurrently after the response.

### R2-9 — completeness

**Problem**

> After item 4, the board list excludes completed and archived projects. The design does not say what the detail sheet does when `?project=` points at one of those projects, for example a link from the completed page, the customer page, the command palette or an email. If the sheet looks the project up in the board's list, it will not find it.

**Remedy**

> Specify that the sheet loads a project by id when it is not in the board list (or state where such links go instead), and include this case in the item 4 checks.

### R2-10 — consistency

**Problem**

> Item 4 moves the calendar to `listBoardProjects`, which excludes completed and archived projects. The document does not confirm that the calendar hides those projects today, and it does not name the data source for command palette search, which may search completed projects now. If either view shows them today, premise 3 is broken.

**Remedy**

> Confirm from code what the calendar, command palette and board show today for completed and archived projects. Give each one a query that keeps that behavior.

### R2-11 — consistency

**Problem**

> Approach B says it costs 'two to three migrations', but Dependencies lists four: the customer_id index, the `reject_gate` reflow, the `sending` outbox status and `save_delegation`.

**Remedy**

### R2-12 — completeness

**Problem**

This original obligation from round 1 is still unmet.

**Remedy**

### R2-13 — feasibility

**Problem**

The old code and the old `email:retry` (which sweeps only `failed` rows) do not handle either state, so those emails are stranded.

**Remedy**
