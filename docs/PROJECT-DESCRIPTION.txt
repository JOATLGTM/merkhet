Merkhet is an internal project-tracking web app I designed and built for Merkhet Architecture, a residential architecture firm. Before it, the status of every project lived in people's heads, email threads, and a spreadsheet, and work sat idle because nobody knew a phase had been handed to them. The firm needed to answer three questions at a glance: where is every project, who owns its current phase, and what is due when.

I built the app as sole developer over seven weeks (August to September 2026) with Next.js 16, React 19, TypeScript, Tailwind CSS, and Supabase for Postgres, authentication, and file storage. It has been in production use since September 2026.

The core is a kanban board with one column per design phase, from Pending through Schematic Design, Design Development, Review, Construction Documents, Final Review, and Permitting. Moving a project is a drag, but the rules are enforced in the database and server actions, not the UI. A project cannot leave Pending until a signed contract is uploaded. It cannot leave Active until a staff member and planned dates are assigned to every phase. Review and Final Review require sign-off from three named parties, and a rejection sends the project back a phase. On hold is a flag rather than a column, so the board shows where a project stalled and for how long. Every move is logged with who and when.

Planned dates and hours feed a calendar timeline, a per-staff workload view, and a billing summary per project and assignee. That arithmetic lives in plain TypeScript modules so it can be verified from the command line without a browser.

Phase changes send email automatically: four templates covering eleven events, split between internal staff notifications and client-facing progress updates. Every message is written to an outbox table before the provider is called, so a failed send is visible and retryable instead of lost. Client email sits behind a feature flag. While it was off, client messages were redirected verbatim to the project owner so the firm could review real rendered mail before any client received one.

Access is invite-only. Admins invite staff by email through Supabase Auth, a database trigger creates the profile before first sign-in, and roles are limited to admin and staff. Clients and outside consultants are records in the system and never log in.

I ran the project spec-first. A product requirements document and a separate workflow specification were the single authority on phase order, gates, and notification routing, and they changed in the same commit as the schema whenever the firm's process changed. Work shipped in dependency-ordered slices across twenty-one database migrations, with a decisions log explaining each tradeoff. Proposed changes went to the firm as dated approval documents with an approve or decline line per item, so nothing shipped on an assumption.
